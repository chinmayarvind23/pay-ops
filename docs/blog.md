# PayOps: investigating Kubernetes payment failures with verifiable evidence

Payment incidents can have similar symptoms even when their causes are different. A processor outage, a failed deployment and memory pressure can each produce unsuccessful requests. In PayOps, the investigation combines Kubernetes state, logs, traces, deployment changes and payment telemetry to produce a ranked diagnosis with references to the observations behind it. The project evaluates whether these references support the diagnosis and whether the system can preserve authorization when an investigation proposes an action.

The experimental environment contains five synthetic services running in local Kubernetes: payments, risk, processor, ledger and webhook. Requests carry synthetic sample IDs and processor, region and payment-method fields. They do not carry account balances or transfer real funds. The scenario suite contains 24 reproducible failures, including OOMKills, bad rollouts, scheduler and HPA saturation, dependency outages, misleading telemetry and payment-slice degradations. Each qualified run retains activation evidence, the original resource configuration and verified cleanup.

The first local model treatment exposed a gap between citation integrity and diagnostic quality. A reference could point to a real artifact without supporting the proposed cause. Compact replay achieved 9/24 Recall@1 and 16/24 Recall@3. A post-hoc review found support for only 15 of its 72 reference links. Retaining source hashes was necessary for reproducing the investigation, but it did not establish semantic attribution.

The revised treatment checks specific observed mechanisms before presenting candidate causes to the model. Examples include PostgreSQL connection exhaustion, an unavailable Redis dependency, resource-pressure events and payment failures isolated to a matched slice. The context builder prioritizes relevant observations while retaining the original artifacts. The expanded corpus preserves the original 28 facts and adds two HTTP observations derived from retained execution receipts. It does not pass scenario labels or injector configuration to the model.

On this development corpus, the predicate-assisted treatment correctly diagnosed 22 of 24 cases, giving 91.7% Recall@1 and Recall@3. The two values are equal because the local contract returns at most one supported cause. Python predicates perform substantial classification in this treatment; the result should not be interpreted as standalone model accuracy. Its 23 emitted support links agree with a development reference that informed the predicates, so this agreement is not an independent attribution study.

The 24 recorded-evidence calls had a median latency of 8.414 seconds and p95 latency of 15.578 seconds, with zero provider charges from local Qwen inference. These measurements exclude live collection and human investigation time. A separate live processor-outage investigation returned PROCESSOR_UNAVAILABLE in 27.578 seconds using one model call. Reopening the completed investigation left its durable records unchanged, and the scenario runner restored healthy payments. This verifies one complete local path; it does not establish the original human-time reduction target.

LangGraph maintains the investigation workflow, while LangChain message types connect the bounded reasoning loop to its model adapter. SQL reservations precede work dispatch, and immutable receipts allow completed observations to be reused. Unknown completion stops automatic redispatch. PostgreSQL provides a durable data integration, Redis caches derived information and Elasticsearch retrieves scoped runbook and incident evidence. OpenTelemetry connects requests across services, and a separate LangSmith exporter sends only explicitly selected receipt metadata.

Remediation is governed by ordinary Python outside the model. The broker checks current identity, incident scope, action type and evidence, requires approval where appropriate, and revalidates before execution. Kubernetes mutations use UID, resource-version and specification preconditions to reject concurrent changes. The component evaluation rejected all 120 unauthorized capability attempts before executor dispatch. These attempts represent five capability classes repeated across 24 contexts, rather than 120 unique attack designs.

Failure-oriented tests also exposed cleanup problems. A failed evidence write could prevent removal of an owned CPU-load Job. A lost namespace-create response could leave an eviction namespace on Kubernetes even though the caller had no returned object to clean up. Recovery now continues owned Job cleanup while retaining the audit failure, and reconciles uncertain namespace creation through the run label and current UID. Foreign state remains untouched and unverified recovery retains the experiment latch.

The protected API now includes GraphQL for nested incident, report and paginated evidence reads. It shares REST authentication and incident scope, with bounds on parsing, depth and selected fields. Slack notifications send incident references through an explicitly configured webhook. Messages contain no retrieved alert prose and cannot approve or execute remediation. The integration tests exercise authorization, malformed queries, delivery failures and unchanged remediation boundaries without sending live Slack messages.

The refreshed full suite passed 2,445 tests before the GraphQL and Slack additions. The final API and remediation checks passed 95 tests with 100% coverage for the three affected modules. Combined module coverage satisfies the configured floors, with the reports identifying which checks ran before and after the integration. The public demo is a sanitized interactive replay hosted on a free Hugging Face Static Space. AWS has self-service setup instructions; Supabase and Vercel are excluded. Optional GCP Terraform and GKE MCP adapters have their verification scope documented separately from a hosted cloud deployment.

The remaining evaluation question is transfer. A held-out scenario set and independent claim review would test whether the observed gains extend beyond the evidence used to develop the predicates. A paired human study would be needed to measure investigation-time savings. The project provides the timing collector and scorer, but reports the measurements available now rather than replacing those studies with estimated results.
